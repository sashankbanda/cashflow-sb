# Code review & audit — 2026-08-06

Adversarial review of money math, authorization, and idempotency across the
core (expenses, balances, settlements, groups, capture, settings). Thirteen
findings; the ones below marked ✅ were fixed and shipped the same day.

## Fixed

1. ✅ **`splitPersonalExpense` could double-book on double-submit/crash-retry** —
   the group expense now uses a deterministic idempotency key derived from the
   source row (`split-personal:<expenseId>`), so replays converge on one expense.
2. ✅ **Idempotency keys were globally unique** — another user could (maliciously
   or by collision) block or shadow an insert, and the conflict lookup returned
   whichever row carried the key. Now unique per `(created_by, idempotency_key)`
   (migration 0012) with owner-scoped conflict lookups.
3. ✅ **Capture key had no date** — recurring payments whose bank SMS is
   byte-identical daily recorded once ever, silently. The key now includes the
   day; same-text re-delivery on the same day still dedupes and no longer
   re-notifies.
4. ✅ **Budget + insights category sums counted income as spend** when an entry's
   direction was flipped while keeping a category — both queries now filter
   `is_income = false`.
5. ✅ **Full data export included groups the user had left** (and everything
   members added after they left). Export now uses active memberships only.
6. ✅ **Category checks were existence-only** — any expense could reference
   another user's private or archived category. All three creation/update paths
   now require system-or-own and not-archived.
7. ✅ **Ghost-name clash check was case-sensitive** while split-by-name matching
   is case-insensitive — "rahul" and "Rahul" could become two ghosts splitting
   debts. Clash check now lower-cases.
8. ✅ **Archived groups accepted joins/claims** via still-valid invite tokens
   (only the landing page checked). Both actions now verify the group is live.
9. ✅ **Deleted accounts left live invite tokens** — now revoked in the same
   transaction.
10. ✅ **`participants`/`payers` arrays were unbounded** — capped at 100.

## Deferred (known, accepted for now)

- **Settlements have no idempotency key and no undo** — a double-tap records a
  payment twice, permanently. Needs a schema column + client key (like
  expenses) and ideally a soft-delete action; the `deleted_at` column already
  exists and every sum honors it.
- **Settlement anchor semantics** — `getCashTotals` anchors settlements by
  server-set `settled_at` (UTC) while expenses use the user-chosen
  `expense_date`; late-recorded pre-anchor settlements overstate the balance
  and can't be backdated. Needs a user-supplied `settled_on` date.
- **`leaveGroup` zero-balance check is TOCTOU** — a concurrent expense naming
  the leaver can commit between check and leave. Needs `SELECT … FOR UPDATE`.
- **No DB uniqueness for ghost names / the auto-"Splits" group** — concurrent
  creates can still race past the app-level checks. Needs partial unique
  indexes (`(group_id, lower(display_name)) WHERE left_at IS NULL`; one live
  "Splits" group per creator).
- **`deleteAccountAction` leaves an ownerless ghost owner** — sole-owner groups
  become un-administerable. Consider ownership transfer or auto-archive.
- **Any member can record a settlement between two other members** — necessary
  for ghosts, but with no undo it lets one member rewrite two claimed users'
  balances. Consider requiring caller involvement when both parties are real.
- **DRY backlog** — the "Split with" chips block is triplicated across
  AddExpenseFlow / PersonalEntrySheet / QuickAddScreen; the back-button link is
  copied across settings pages; the duplicate-guard client pattern is doubled.
  Consolidate when next touching those files.

## Verified clean

Action pipeline (session → rate limit → zod → typed errors); every one of the
18 money aggregations guards `deleted_at`; personal-entry CRUD ownership
checks; group modify authorization; viewer-share vs cash-true math (ledger and
budgets sum shares, `paid_out` sums payer rows, the Home hero composes them
without double-counting); the split engine's paise-exact invariants and DB
check constraints; capture token strength and rotation; invite join races
(covered by the existing partial unique index).
